## 📘 초보자를 위한 안내

**프런트엔드가 뭔가요?**

사용자 **눈에 보이는 쪽** 전부입니다. 화면, 버튼, 글씨, 손가락으로 밀어 넘기는 동작. 브라우저 안에서 도는 코드입니다.

**왜 이것도 설계가 필요한가요?**

화면 하나 만드는 건 어렵지 않습니다. 문제는 화면이 20개가 되고, 그 20개가 서로 정보를 주고받고, 각각 로딩·오류·빈 상태를 가질 때입니다. 아무 규칙 없이 만들면 **비슷한 코드가 20벌 생기고, 하나 고칠 때 19개를 못 찾습니다.**

**이 문서에서 가장 중요한 세 곳**

1. **§3 디렉터리 구조** — 파일을 어떤 폴더로 나눌지
2. **§4 레이어 규칙** — 폴더들이 서로를 부르는 방향
3. **§6 상태 관리** — "지금 화면이 알고 있는 값"을 누가 갖고 있을지

**§6이 왜 어려운 주제인가요?**

화면에는 여러 종류의 "지금 값"이 있습니다.
- 서버에서 받아온 전시 정보
- 지금 보고 있는 그림이 몇 번째인지
- 팝업이 열려 있는지
- 사용자가 입력하다 만 글자

이걸 전부 한 통에 넣으면 화면이 조금만 복잡해져도 감당이 안 됩니다. 그래서 **성격에 따라 네 곳으로 나눠서** 보관합니다. 이 결정이 프런트엔드 코드의 수명을 좌우합니다.

**읽는 요령** — 비개발자라면 §5 라우팅(화면 주소 목록), §9 성능, §10 PWA·알림, §11 접근성만 봐도 서비스가 어떻게 동작할지 감이 옵니다. 모르는 단어는 [용어 사전](00-용어사전.md)에서. 원문은 `../05-FRONTEND-ARCHITECTURE.md`입니다.

## 1. 설계 원칙

> **📘 쉬운 설명**
>
> **FA-2(기능은 폴더 하나로 완결)**가 실용적인 원칙입니다.
>
> "설정 화면을 지운다"고 했을 때, 폴더 하나만 지우면 끝나야 합니다. 만약 설정 화면 코드가 5개 폴더에 흩어져 있으면 **지우다가 뭘 빠뜨렸는지 모르게** 되고, 결국 아무도 안 쓰는 코드가 계속 쌓입니다.
>
> **FA-7(실패해도 화면은 뜬다)**도 이 서비스의 성격을 보여줍니다. 방문 기록 전송이 실패했다고 그림이 안 보이면 안 됩니다.

| # | 원칙 | 적용 |
|---|---|---|
| **FA-1** | **레이어 의존은 한 방향** | `app → features → entities → shared`. 역방향·수평 참조를 정적 검사로 금지한다 |
| **FA-2** | **기능은 폴더 하나로 완결** | 한 화면을 지우면 폴더 하나가 지워져야 한다. 화면 코드가 5개 디렉터리에 흩어지는 구조를 만들지 않는다 |
| **FA-3** | **서버 상태와 클라이언트 상태를 섞지 않는다** | 서버에서 온 것은 TanStack Query가, 화면 조작 상태는 컴포넌트 지역 상태 또는 소형 스토어가 소유한다 |
| **FA-4** | **API 계약은 한 곳에서만 안다** | `shared/api`가 봉투·오류·페이지네이션을 흡수하고, 그 바깥은 도메인 타입만 다룬다 |
| **FA-5** | **디자인 토큰 밖으로 나가지 않는다** | 임의 값·인라인 스타일을 린트로 차단한다(디자인 문서 DS-7) |
| **FA-6** | **첫 화면을 가장 빨리** | 라우트 단위 코드 스플리팅, 관리자 번들의 관람자 경로 유입 금지 |
| **FA-7** | **실패해도 화면은 뜬다** | 기록 API 실패, 이미지 실패, 네트워크 단절이 화면 전체를 무너뜨리지 않는다(PRD §6.1, §6.7) |

## 2. 기술 선택

> **📘 쉬운 설명**
>
> 어떤 도구를 쓸지와 **왜 다른 걸 안 골랐는지**를 함께 적었습니다.
>
> 주요 도구를 일상어로 옮기면,
>
> | 이름 | 하는 일 |
> |---|---|
> | **React** | 화면을 조각으로 나눠 만드는 도구 |
> | **React Router** | 주소에 따라 어떤 화면을 보여줄지 정하는 도구 |
> | **TanStack Query** | 서버에서 받아온 정보를 관리·재사용하는 도구 |
> | **Zustand** | 화면이 기억하는 값 몇 개를 담아두는 작은 통 |
> | **React Hook Form + Zod** | 입력 폼과 검증 |
> | **Tailwind** | 스타일을 짧은 이름으로 붙이는 도구 |
> | **Vite** | 개발 중 화면을 띄우고 배포용 파일을 만드는 도구 |
> | **Workbox** | 오프라인 저장과 알림을 다루는 도구 |
>
> **"기각 사유"를 적어두는 습관**이 중요합니다. 나중에 누군가 "이거 왜 A 안 쓰고 B 썼어요?"라고 물을 때, 문서가 답합니다.

| 영역 | 선택 | 근거 · 대안 기각 사유 |
|---|---|---|
| 라우팅 | **React Router 7** (`createBrowserRouter`) | 데이터 라우터의 `loader`로 라우트 진입 시 프리페치 가능. TanStack Router는 학습 비용 대비 이점이 적다 |
| 서버 상태 | **TanStack Query 5** | 캐시·재검증·오프라인 재시도를 직접 구현하지 않는다. `staleTime`으로 전시 데이터 특성(하루 단위 불변)을 그대로 표현할 수 있다 |
| 클라이언트 상태 | **Zustand 5** (스토어 3개 이하) | Context 남용은 리렌더 폭발을 부른다. Redux는 이 규모에 과하다 |
| 폼 | **React Hook Form 7 + Zod 4** | 비제어 기반이라 입력 지연이 없다. 서버 `field_errors`를 그대로 주입할 수 있다 |
| 스타일 | **TailwindCSS 3 + CVA + tailwind-merge** | 디자인 문서 §11 |
| 아이콘 | 자체 SVG 스프라이트 | 의존성 0, 트리셰이킹 고민 없음 |
| 날짜 | **`date-fns` (필요 함수만)** | 표시 문자열은 대부분 서버가 준다(API 문서 §6.1). 클라이언트 날짜 연산은 최소 |
| PWA | **`vite-plugin-pwa` (Workbox)** | 서비스워커 수기 작성 금지. 푸시 핸들러만 커스텀 주입 |
| 테스트 | **Vitest + Testing Library + Playwright + MSW** | |
| 린트 | **oxlint**(기존) + **dependency-cruiser**(레이어) + **prettier-plugin-tailwindcss** | 레이어 규칙은 oxlint로 표현되지 않으므로 별도 도구를 쓴다 |
| 이미지 | 네이티브 `<img>` + LQIP | 라이브러리 불필요 |
| 드래그 | **`@dnd-kit/core`** (관리자 번들 한정) | 순서 변경(B-2)에만 필요하며 관람자 번들에 들어가지 않는다 |

## 3. 디렉터리 구조

> **📘 쉬운 설명 — 이 문서의 본론**
>
> 폴더 배치도입니다. 큰 덩어리는 4개뿐입니다.
>
> | 폴더 | 하는 일 | 비유 |
> |---|---|---|
> | `app/` | 앱 전체의 뼈대 — 주소 연결, 공통 설정 | 건물의 골조와 배선 |
> | `features/` | **화면 하나하나** | 각각의 방 |
> | `entities/` | 여러 화면이 함께 쓰는 도메인 개념 | 여러 방에 쓰이는 공용 가구 |
> | `shared/` | 도메인을 전혀 모르는 공용 부품 | 못, 나사, 경첩 |
>
> `features/` 안을 보면 `landing`(첫 화면), `auth`(로그인·가입), `gallery`(갤러리), `artwork`(그림), `archive`(지난 전시), `settings`(설정), `admin`(관리자)로 나뉩니다. **화면 지도와 폴더가 1:1로 맞습니다.**
>
> 각 폴더 안의 `index.ts`가 **그 폴더의 출입구**입니다. 다른 곳에서는 이 출입구를 통해서만 접근할 수 있고, 안쪽 파일을 직접 건드릴 수 없습니다.

    │   │   ├── constants.ts         # ARTWORK_COUNT=12, ARCHIVE_LIMIT=30 …
    │   │   └── messages.ts          # 마이크로카피 전량(UX 문서 §5). 문구의 단일 원천
    │   ├── types/

### 3.1 배치 판단 기준

> **📘 쉬운 설명**
>
> "새 파일을 어디 둘까?"에 답하는 질문 4개입니다.
>
> 실제 예로 보면,
> - 갤러리 화면에서만 쓰는 격자 → `features/gallery/`
> - 갤러리에도 아카이브에도 나오는 썸네일 → `entities/artwork/`
> - 아무 데나 쓰는 버튼 → `shared/ui/`

| 질문 | 위치 |
|---|---|
| 특정 화면에서만 쓰이는가? | `features/{기능}/` |
| 두 개 이상의 기능이 같은 도메인 개념을 다루는가? | `entities/{도메인}/` |
| 도메인을 전혀 모르는가? | `shared/` |
| 라우팅·프로바이더·레이아웃인가? | `app/` |

**`features/*/index.ts`만이 외부 공개 표면이다.** 다른 기능의 내부 파일을 직접 import 하는 것을 dependency-cruiser가 차단한다.

## 4. 레이어 규칙

> **📘 쉬운 설명**
>
> 폴더들이 **서로를 부르는 방향**입니다. `app → features → entities → shared` 한 방향으로만 갑니다.
>
> **금지 사항 5개 중 1번이 가장 중요합니다** — 화면끼리 서로를 부르지 못하게 합니다.
>
> 예를 들어 설정 화면이 갤러리 화면의 무언가를 갖다 쓰기 시작하면, 갤러리를 고칠 때 설정이 망가집니다. 공통으로 필요한 게 생기면 **아래층(`entities` 또는 `shared`)으로 내려서** 양쪽이 거기서 가져다 씁니다.

### 4.1 의존 방향

| 레이어 | import 허용 대상 |
|---|---|
| `app` | `features`, `entities`, `shared` |
| `features` | 같은 feature 내부, `entities`, `shared` |
| `entities` | 같은 entity 내부, `shared` |
| `shared` | `shared`만 |

**금지 사항**

1. `features` 간 상호 참조 (공통이 필요하면 `entities` 또는 `shared`로 올린다)
2. `entities` → `features`
3. `shared` → 상위 레이어
4. `features/*/` 내부 파일을 다른 곳에서 깊게 참조 (`index.ts` 경유만)
5. 순환 의존

`.dependency-cruiser.cjs`가 이 5개를 규칙으로 갖고 CI에서 실패시킨다.

### 4.2 컴포넌트 소속 판정

> **📘 쉬운 설명**
>
> 디자인 시스템 문서의 부품 목록과 이 문서의 폴더가 **어떻게 대응하는지**의 표입니다.
>
> 기준은 **"이 부품이 도메인을 아는가"**입니다.
> - 버튼은 갤러리인지 쇼핑몰인지 모릅니다 → `shared/ui`
> - 썸네일은 "그림"이라는 개념을 압니다 → `entities/artwork/ui`
> - 전시 헤더는 이 서비스의 화면 구성을 압니다 → `features/gallery/components`
>
> (이 표는 교차 검토에서 추가된 부분입니다.)

디자인 시스템 카탈로그(디자인 문서 §8)와 이 문서의 디렉터리는 다음과 같이 대응한다.

| 카탈로그 구분 | 위치 | 예 |
|---|---|---|
| 프리미티브(§8.1) | `shared/ui/` | `Button`, `TextField`, `Dialog`, `Banner`, `StatusChip` |
| 도메인 표현(§8.2 일부) | `entities/{도메인}/ui/` | `ArtworkThumb`, `ExhibitionTitle`, `DateLine`, `PositionIndicator` |
| 화면 전용 조합 | `features/{기능}/components/` | `ExhibitionHeader`(= `DateLine` + `ExhibitionTitle` + 연장 라벨), `GalleryFooterNav`, `NotifySection` |

**같은 이름을 두 계층에 두지 않는다.** 화면 전용 조합은 이름에 문맥을 담아(`ExhibitionHeader`) 도메인 표현 컴포넌트(`ExhibitionTitle`)와 구분한다.

### 4.3 shared/ui의 계약

> **📘 쉬운 설명**
>
> **`shared/ui`의 부품은 이 서비스에 대해 아무것도 몰라야 합니다.**
>
> 버튼 부품이 "전시"라는 개념을 알기 시작하면, 그 버튼은 다른 프로젝트에 못 갖다 씁니다. 더 나쁜 건, 전시 관련 변경이 있을 때마다 **버튼 코드를 고쳐야 한다**는 점입니다.

`shared/ui` 컴포넌트는 **도메인 타입을 프롭으로 받지 않는다.** `ArtworkThumb`이 `shared/ui`가 아니라 `entities/artwork/ui`에 있는 이유가 이것이다. 이 경계가 흐려지면 디자인 시스템이 제품에 종속되어 재사용이 불가능해진다.

## 5. 라우팅

> **📘 쉬운 설명**
>
> **라우팅**은 "주소창에 뭐가 있으면 어떤 화면을 보여줄까"입니다. `/gallery`면 갤러리 화면, `/settings`면 설정 화면.

### 5.1 경로 표

> **📘 쉬운 설명**
>
> 화면 전체 목록입니다. 열의 뜻은,
>
> - **레이아웃** — 공통 틀. `Gallery`는 관람자용 좁은 화면, `Studio`는 관리자용 넓은 화면
> - **가드** — 들어갈 수 있는 사람. "회원"은 로그인해야, "큐레이터"는 관리자만
> - **번들** — 코드 파일 묶음. "초기"는 앱을 켤 때 바로 받고, "지연"은 그 화면에 갈 때 받습니다
>
> **`:artworkId` 처럼 콜론이 붙은 부분**은 자리 표시자입니다. 실제로는 `/gallery/artworks/a3f9...` 같은 주소가 됩니다.
>
> 마지막 줄이 실용적입니다 — 주소 문자열은 파일 한 곳에만 적어두고, 모든 링크가 그걸 가져다 씁니다. 주소를 바꿀 때 한 곳만 고치면 됩니다.

### 5.2 아카이브 경로 설계

> **📘 쉬운 설명**
>
> "지난 전시"를 보는 화면은 오늘의 갤러리 화면과 **거의 똑같이 생겼습니다.** 다른 건 위쪽 안내 바("지난 전시를 보고 있습니다")뿐입니다.
>
> 그래서 화면을 복사해 두 벌 만들지 않고, **같은 화면에 "지금은 아카이브 모드"라는 표시만 넘깁니다.** 복사해두면 나중에 갤러리 화면을 고칠 때 아카이브 쪽을 반드시 빠뜨립니다.
>
> 두 번째 문단은 교차 검토에서 발견한 문제입니다. **지난 전시를 보다가 그림을 열고 뒤로 가면 오늘의 전시로 튕겨 나가는** 문제가 있었습니다. 그래서 아카이브용 그림 주소를 따로 만들었습니다. **주소에 "어디서 왔는지"가 담겨 있어야 제대로 돌아갈 수 있습니다.**

`/archive/:date`가 `/gallery`와 **동일한 컴포넌트를 재사용**한다. 차이는 데이터 소스(`GET /exhibitions/{date}` vs `/current`)와 상단 안내 배너(`지난 전시를 보고 있습니다` + 오늘로 돌아가기)뿐이다(PRD §6.8). 컴포넌트를 복제하지 않고 `mode: 'current' | 'archive'` 프롭으로 분기한다.

**그림 화면도 같은 원리로 두 경로를 갖는다.** `/gallery/artworks/:id`와 `/archive/:date/artworks/:id`는 같은 컴포넌트를 렌더하되 되돌아가기 대상이 다르다 — 전자는 오늘의 갤러리로, 후자는 그 날짜의 갤러리로 돌아간다. **경로에 문맥을 담지 않으면 아카이브에서 그림을 연 사람이 뒤로 갔을 때 오늘의 전시로 튕겨 나간다.** 되돌아가기 대상은 `useGalleryContext()` 훅이 현재 라우트에서 파생하며, 컴포넌트는 문맥을 직접 판단하지 않는다.

### 5.3 가드

> **📘 쉬운 설명**
>
> **가드**는 화면에 들어가기 전 검문입니다. 로그인 안 했으면 로그인 화면으로 보냅니다.
>
> 마지막 문단이 실전에서 중요합니다 — **세션 확인이 끝나기 전에는 판단하지 않습니다.**
>
> 이걸 안 지키면, 새로고침할 때마다 "로그인 화면이 0.3초 번쩍하고 갤러리로 넘어가는" 현상이 생깁니다. 실제로는 로그인되어 있는데, 확인이 끝나기 전에 "로그인 안 된 것 같은데?"라고 판단해버리기 때문입니다.
>
> `RequireCurator`의 처리도 세심합니다. 일반 회원이 관리자 주소로 들어오면 오류를 띄우지 않고 **조용히 갤러리로 보냅니다.**

| 가드 | 동작 |
|---|---|
| `RequireAuth` | 세션 확인 전에는 스플래시 유지. 미인증이면 `/login?next={경로}`로 치환 이동 |
| `RequireCurator` | 미인증 → `/login`, 회원이지만 비큐레이터 → `/gallery`로 조용히 이동(관리자 존재를 노출하지 않음) |
| `RedirectIfAuthed` | 로그인·가입 화면에서 이미 세션이 있으면 `/gallery` |
| `RequirePasswordChange` | `must_change_password`이면 `/password/change`로 강제. 예외는 로그아웃 경로뿐 |

가드는 **세션 부트스트랩 완료 후에만** 판정한다. 미완료 상태에서 리다이렉트하면 새로고침마다 로그인 화면이 번쩍인다.

### 5.4 코드 스플리팅

> **📘 쉬운 설명**
>
> **코드 스플리팅**은 코드를 여러 조각으로 나눠서, 지금 필요한 것만 내려받게 하는 것입니다.
>
> 여기서 중요한 건 **관리자 코드를 관람자가 받지 않게 하는 것**입니다. 관리자 화면은 이 서비스에서 딱 한 사람만 쓰는데, 그 코드가 관람자 첫 화면 로딩에 섞이면 **99명이 쓰지도 않을 코드를 매일 아침 내려받게** 됩니다.
>
> 마지막 굵은 문장이 좋은 장치입니다. 사람이 실수로 섞어놓을 수 있으니, **빌드할 때 기계가 확인해서 섞여 있으면 빌드를 실패**시킵니다.

| 청크 | 포함 | 목표 크기(gzip) |
|---|---|---|
| `main` | 셸·라우터·프로바이더·shared/ui 핵심·세션·A·A-1 | ≤ 60KB |
| `gallery` | C·C-2 | ≤ 35KB |
| `gallery-extra` | C-1·C-3·C-4 | ≤ 20KB |
| `admin` | B 계열 전부 + `@dnd-kit` | ≤ 120KB |
| `vendor-react` | react·react-dom·router | ≤ 60KB |
| `vendor-query` | TanStack Query | ≤ 15KB |

**관리자 청크는 관람자 경로에서 절대 로드되지 않는다.** `RequireCurator` 라우트 아래에서만 `lazy()`로 참조하며, 번들 분석 스크립트가 관람자 청크에 admin 모듈이 섞이면 빌드를 실패시킨다.

## 6. 상태 관리

> **📘 쉬운 설명 — 프런트엔드에서 가장 중요한 결정**
>
> **상태**는 "화면이 지금 알고 있는 값"입니다.
>
> 초보자가 가장 흔히 하는 실수가 **모든 상태를 한 곳에 몰아넣는 것**입니다. 처음엔 편하지만, 화면이 늘어나면 어떤 값이 어디서 바뀌는지 아무도 모르게 됩니다.
>
> 그래서 성격에 따라 나눕니다.

### 6.1 상태의 4분류

> **📘 쉬운 설명**
>
> 네 종류를 구별하는 기준은 **"이 값의 진짜 주인이 누구인가"**입니다.
>
> | 종류 | 주인 | 예 |
> |---|---|---|
> | 서버 상태 | 서버 | 전시 정보, 회원 목록 |
> | URL 상태 | 주소창 | 지금 보는 그림, 목록 필터 |
> | 전역 클라이언트 상태 | 앱 전체 | 로그인 정보, 토스트 |
> | 지역 상태 | 그 화면 | 입력 중인 글자, 팝업 열림 |
>
> **"목록의 필터를 주소에 둔다"**가 실용적인 결정입니다. 관리자가 "차단된 회원만" 필터를 걸어놓고 새로고침했을 때 필터가 풀려버리면 짜증나고, 그 상태를 동료에게 링크로 보낼 수도 없습니다.

| 종류 | 소유자 | 예 |
|---|---|---|
| **서버 상태** | TanStack Query | 전시, 그림, 회원 목록, 설정 |
| **URL 상태** | React Router | 현재 그림 ID, 아카이브 날짜, 목록 필터·페이지 |
| **전역 클라이언트 상태** | Zustand (3개 스토어) | 세션, 토스트, 뷰어 |
| **지역 상태** | `useState`/`useReducer` | 폼 입력, 열림/닫힘, 스와이프 진행 |

**목록의 필터·검색어·페이지는 URL에 둔다.** 관리자가 특정 필터 상태를 새 탭으로 열거나 새로고침해도 유지되어야 한다.

### 6.2 Zustand 스토어

> **📘 쉬운 설명**
>
> 앱 전체가 공유하는 값을 담는 통을 **딱 3개만** 만듭니다.
>
> 마지막 굵은 문장이 좋은 자기 점검입니다 — **"통을 4개째 만들고 싶어지면, 그 값은 사실 서버 상태거나 주소 상태다."**
>
> 실제로 대부분 그렇습니다. 이 한 줄이 있으면 나중에 통이 무한정 늘어나는 걸 막을 수 있습니다.

| 스토어 | 상태 | 비고 |
|---|---|---|
| `sessionStore` | `user`, `status`(`booting`/`authenticated`/`anonymous`), `mediaExpiresAt` | 서버 상태이기도 하지만 라우팅 가드가 동기적으로 읽어야 하므로 스토어에 미러링한다. **원천은 Query이고 스토어는 구독 결과를 반영**한다 |
| `toastStore` | 현재 토스트 1개 | 동시 1개(디자인 문서 §8.1) |
| `viewerStore` | 전체화면 뷰어 열림 여부·대상 그림·줌 상태 | 라우팅과 무관한 오버레이 |

**스토어를 4개째 만들고 싶어지면 그 상태가 서버 상태거나 URL 상태다.** 재검토한다.

### 6.3 Query 정책

> **📘 쉬운 설명**
>
> 서버에서 받아온 정보를 **얼마나 오래 재사용할지** 정합니다.
>
> - **`staleTime`** — "이 시간 동안은 새로 안 받아도 됨"
> - **`refetchOnFocus`** — 다른 앱 보다가 돌아왔을 때 다시 받을지
>
> 표에서 재미있는 건 **과거 전시의 `staleTime`이 "무한"**인 점입니다. 지나간 전시는 절대 안 바뀌므로 한번 받으면 다시 받을 이유가 없습니다.
>
> 반대로 **관리자 화면은 0**입니다. 큐레이터가 방금 바꾼 게 화면에 안 보이면 혼란스럽기 때문입니다.
>
> **정보의 성질에 따라 다르게 다루는 것**, 이게 서버 상태 관리의 핵심입니다.

| 대상 | staleTime | gcTime | refetchOnFocus | 비고 |
|---|---|---|---|---|
| `/public/landing` | 60초 | 10분 | O | |
| `/exhibitions/current` | 5분 | 24시간 | O | 포커스 복귀 시 새 전시 확인 |
| `/exhibitions/{date}` | 무한 | 24시간 | X | 과거 전시는 불변 |
| `/exhibitions` (아카이브) | 5분 | 1시간 | X | 무한 스크롤 |
| `/artworks/{id}` | 무한 | 24시간 | X | |
| `/me` | 5분 | 1시간 | O | |
| 관리자 달력·편집 | 0 | 5분 | O | 운영 데이터는 항상 최신 |
| 통계 | 60초 | 10분 | O | |

**전역 기본값** — `retry`: 네트워크·5xx만 2회(지수 백오프 300ms→1.2s), 4xx는 재시도 없음. `throwOnError`: 라우트 경계에서만 true.

### 6.4 낙관적 업데이트

> **📘 쉬운 설명**
>
> **낙관적 업데이트**는 "서버 답을 기다리지 않고 일단 화면부터 바꾸는 것"입니다.
>
> 알림 스위치를 껐을 때 0.3초 뒤에 꺼지면 답답합니다. 그래서 **일단 꺼진 것처럼 보여주고**, 서버가 실패하면 되돌립니다.
>
> 그런데 표를 보면 **차단·숨김에는 이걸 안 씁니다.** 되돌리기 어려운 조작에서 "된 것처럼 보였다가 사실은 안 됐다"는 일이 벌어지면, 큐레이터는 차단이 됐다고 믿고 넘어갑니다. **위험한 동작은 확실히 확인하고 보여줍니다.**

| 대상 | 처리 |
|---|---|
| C-4 알림 on/off, 큰 글씨 | **낙관적 반영.** 실패 시 롤백 + 토스트 |
| 관리자 자동 저장 | 낙관적이지 않다. `SaveIndicator`로 진행 상태를 명시 |
| 차단·숨김 | 낙관적이지 않다. 되돌리기 어려운 조작은 서버 응답을 기다린다 |
| 열람 표식 | 낙관적 반영(즉시 표식 표시). 기록 API 실패해도 롤백하지 않는다 |

## 7. API 계층

> **📘 쉬운 설명**
>
> 서버와 이야기하는 부분을 **한 곳에 몰아두는** 이야기입니다.
>
> 화면 코드 여기저기서 직접 서버를 부르면, 로그인 만료 처리·오류 처리·재시도 같은 것을 **매번 다시 써야** 하고 반드시 어딘가는 빠뜨립니다.

### 7.1 `httpClient`의 책임

> **📘 쉬운 설명**
>
> 서버와 이야기하는 창구 하나가 도맡는 7가지 일입니다. 중요한 것 몇 개:
>
> - **2번** — API 문서의 "봉투"를 여기서 뜯습니다. 화면 코드는 봉투의 존재를 아예 모릅니다
> - **5번** — 로그인이 만료되면 **한 번만** 로그인 화면으로 보냅니다. "한 번만"이 중요한 이유는, 화면 하나가 서버를 5번 부르는 중에 만료되면 리다이렉트가 5번 겹쳐 일어날 수 있기 때문입니다
> - **6번** — 오류에 요청 번호를 남겨둡니다. 사용자가 "이상해요"라고 할 때 그 번호로 서버 기록을 찾습니다
>
> 마지막 문단 — **다른 곳에서 서버를 직접 부르는 것을 금지**하고 기계가 검사합니다.

1. 기본 URL·`credentials: 'include'`·`X-Requested-With` 헤더 부착
2. 응답 봉투 해석 → 성공이면 `data`만 반환, 실패면 `ApiError`를 throw
3. `304` 처리(Query 캐시 유지)
4. 네트워크 오류를 `ApiError(code: 'NETWORK_OFFLINE')`으로 정규화
5. `401 AUTH_SESSION_EXPIRED`/`AUTH_SESSION_REVOKED` 수신 시 **세션 초기화 + `/login` 이동**을 1회만 트리거
6. `meta.request_id`를 오류 객체에 보존(사용자 문의 대응)
7. 요청 타임아웃 10초(`AbortController`)

**httpClient 바깥에서 `fetch`를 직접 호출하는 것을 린트로 금지한다.** 예외는 서비스워커와 S3 직접 업로드 두 곳뿐이며 각각 별도 모듈(`features/notification/lib`, `features/admin/exhibition-editor/hooks/useUploadQueue`)에 격리한다.

### 7.2 오류 표시 규칙

> **📘 쉬운 설명**
>
> 오류가 났을 때 **어디에 무엇을 보여줄지**의 표입니다.
>
> 핵심은 **입력값 오류는 그 입력칸 옆에** 붙이고, 나머지는 상황에 따라 배너나 토스트로 띄우는 것입니다. "비밀번호가 짧습니다"를 화면 맨 위에 띄우면 사용자는 어느 칸이 문제인지 다시 찾아야 합니다.
>
> 마지막 문단도 중요합니다 — **문구는 서버가 준 걸 그대로 씁니다.** 화면이 자기 나름대로 문구를 만들면, 서버 쪽에서 문구를 다듬어도 화면에는 반영되지 않아 두 곳이 어긋납니다.

| 조건 | 표시 |
|---|---|
| `field_errors`가 있다 | 각 필드 옆에 인라인 표시 (RHF `setError`로 주입) |
| 폼 맥락이고 `field_errors`가 없다 | 폼 상단 배너 |
| 조회 실패(초기 로드) | `ErrorState` + 재시도 |
| 조회 실패(갱신) | 기존 내용 유지 + 토스트 |
| 액션 실패 | 토스트 |
| 오프라인 | 상단 고정 안내 바 |

문구는 **서버의 `error.message`를 우선 사용**하고, 없거나 네트워크 오류인 경우에만 `errorMessages.ts`의 폴백을 쓴다. 프런트가 코드별 문구를 자체 정의해 서버와 어긋나는 상황을 만들지 않는다(FA-4).

### 7.3 쿼리 키 팩토리

각 entity의 `api/keys.ts`가 키를 소유한다. 문자열 배열을 사용처에서 직접 조립하지 않는다.

| 도메인 | 키 형태 |
|---|---|
| exhibition | `['exhibition','current']` / `['exhibition','date',date]` / `['exhibition','archive',{limit}]` |
| artwork | `['artwork','detail',id]` |
| session | `['session']` / `['me']` |
| admin | `['admin','calendar',{from,to}]` / `['admin','exhibition',date]` / `['admin','members',params]` |

무효화는 접두 매칭으로 한다 — 전시 저장 후 `['admin']`과 `['exhibition']`을 무효화하면 관련 화면이 모두 갱신된다.

### 7.4 타입 경계

> **📘 쉬운 설명**
>
> 서버는 `exhibition_date`처럼 **밑줄** 방식으로 이름을 쓰고, 화면 코드는 `exhibitionDate`처럼 **대문자** 방식을 씁니다. 이 둘을 변환하는 지점을 한 곳으로 정합니다.
>
> 마지막 문단이 변환의 진짜 이유입니다. 이름 통일이 목적이 아니라, **서버가 필드 이름을 바꿨을 때 고칠 곳이 한 군데뿐이게** 하는 것입니다. 변환 없이 서버 이름을 화면 전체에서 그대로 쓰면, 서버가 이름 하나 바꿀 때 화면 50곳을 고쳐야 합니다.

`shared/api/types.ts`가 **서버 원형(snake_case)** 타입을 갖고, entity의 `model/types.ts`가 **도메인 타입(camelCase)** 을 갖는다. 변환은 entity의 `api/` 안에서만 일어난다.

이 변환을 두는 이유는 명명 통일이 아니라 **API 변경의 파급 차단**이다. 서버가 필드를 바꾸면 수정 지점이 entity 한 곳이다.

## 8. 화면 조립 규칙

> **📘 쉬운 설명**
>
> 화면 하나를 만들 때의 **공통 골격**입니다. 모든 화면이 같은 모양으로 생기면, 처음 보는 화면도 금방 읽힙니다.

### 8.1 페이지 컴포넌트의 구조

> **📘 쉬운 설명**
>
> 화면 파일은 항상 **3단계**로 씁니다.
>
> 1. 정보 가져오기 (훅 호출)
> 2. 로딩·오류·빈 상태 처리
> 3. 실제 화면 조립
>
> 2번을 **화면 파일에서 눈에 보이게** 처리하라는 게 규칙입니다. 하위 부품에게 맡겨두면, 어떤 화면은 로딩 표시가 있고 어떤 화면은 없는 상태가 됩니다.

모든 `*Page.tsx`는 동일한 골격을 갖는다: **(1) 데이터 훅 호출 → (2) 상태 분기(로딩/오류/빈) → (3) 프레젠테이션 컴포넌트 조합**. 페이지에 비즈니스 계산이나 fetch 호출을 직접 두지 않는다.

| 규칙 | 내용 |
|---|---|
| 데이터 접근 | 반드시 훅 경유(`useCurrentExhibition` 등) |
| 상태 분기 | 로딩·오류·빈 상태를 페이지가 명시적으로 렌더한다. 하위 컴포넌트에 위임하지 않는다 |
| 부수효과 | `useEffect`는 기록 전송·포커스 이동·스크롤 복원에만 |
| 프롭 드릴링 | 2단계까지 허용. 그 이상이면 컴포넌트 분해가 잘못된 것이다 |
| 되돌아가기 | 페이지가 `BackLink`의 대상을 명시적으로 지정한다. 하위 컴포넌트가 `history.back()`을 호출하지 않는다 |

### 8.2 부팅 시퀀스

> **📘 쉬운 설명**
>
> 앱을 켰을 때 **무엇부터 하는지**의 순서입니다.
>
> **낙관적 병렬화** 부분이 재미있습니다. 원래는 "로그인됐나 확인 → 되어 있으면 전시 가져오기" 순서라 두 번 왕복해야 합니다.
>
> 그런데 **"지난번에 로그인되어 있었다"는 메모**가 남아 있으면, 확인과 전시 가져오기를 **동시에** 시작합니다. 대부분의 경우 맞으니 화면이 한 박자 빨리 뜨고, 틀렸으면 진행 중인 요청을 취소하고 로그인으로 보냅니다.
>
> **미디어 쿠키** 부분은 그림을 볼 수 있는 임시 열쇠를 갱신하는 이야기입니다. 이게 만료되면 **그림 전부가 한꺼번에 안 보이므로**, 만료 10분 전에 미리 갱신하고 그래도 실패하면 강제로 다시 받습니다.

1. `main.tsx` — 프로바이더 마운트, 스플래시(정적 HTML) 유지
2. `SessionProvider` — `GET /auth/session` 1회. 완료 전까지 라우터 렌더 보류
3. 세션 결과에 따라 라우터 진입
4. `/` 진입 시 `GET /public/landing`, `/gallery` 진입 시 `GET /exhibitions/current`

**미디어 쿠키 유지** — `GET /auth/session` 응답의 `media_session_expires_at`을 보관하고, 만료 10분 전 또는 앱이 포그라운드로 복귀했을 때 만료가 임박했으면 `POST /media/session`을 호출한다. 갱신 실패 시 이미지가 403으로 깨지므로, 이미지 로드 실패가 연속 3회 발생하면 쿠키 갱신을 1회 강제 시도한 뒤 재시도한다.

**낙관적 병렬화** — 로컬 스토리지에 "이전 방문에서 인증됨" 마커가 있으면 세션 확인과 `/exhibitions/current`를 **동시에** 시작한다. 세션이 무효로 판명되면 진행 중 요청을 취소하고 로그인으로 보낸다. 이 최적화가 C 화면 도달을 1회 왕복만큼 단축한다(API 문서 §11.1).

### 8.3 스크롤 복원

> **📘 쉬운 설명**
>
> 격자에서 아래쪽 그림을 보려고 스크롤한 뒤, 그림 하나를 열고 다시 뒤로 갔을 때 **원래 있던 자리로 돌아가는 것**입니다.
>
> 사소해 보이지만, 이게 안 되면 매번 맨 위로 튕겨서 아래쪽 그림을 볼 때마다 다시 스크롤해야 합니다.
>
> 마지막 문장이 이 문제의 함정입니다. 이미지가 나중에 도착하면 화면 높이가 나중에 정해지고, 그러면 **복원한 자리가 엉뚱한 곳이 됩니다.** 그래서 §9.2의 "종횡비 미리 잡기"가 여기서도 필요합니다.

C(갤러리 그리드) → C-2(그림) → 뒤로가기에서 **그리드 스크롤 위치를 복원**한다. React Router의 기본 복원에 더해 그리드 컨테이너의 스크롤 오프셋을 `sessionStorage`에 라우트 키별로 저장한다. 이미지 지연 로딩 때문에 높이가 나중에 확정되므로, 그리드는 **종횡비 예약으로 초기 높이를 확정**해 복원이 어긋나지 않게 한다.

### 8.4 관리자 미리보기의 컴포넌트 재사용

> **📘 쉬운 설명**
>
> 큐레이터가 "관람자에게 어떻게 보일까"를 확인하는 미리보기 화면입니다.
>
> 여기서 관람자 화면을 **똑같이 흉내내어 다시 만들면** 반드시 어긋납니다. 갤러리를 고칠 때 미리보기를 함께 고치는 걸 잊게 되고, 그러면 미리보기가 거짓말을 하게 됩니다.
>
> 그래서 **같은 부품을 그대로 씁니다.** 이를 위해 갤러리 화면을 "정보를 받아오는 부분"과 "받은 정보를 그리는 부분"으로 나눠두었습니다. 미리보기는 뒤쪽만 씁니다.
>
> 마지막 문단이 이 분리의 보너스입니다. 미리보기는 자연히 방문 기록도 안 남깁니다 — 기록 기능은 앞쪽에 붙어 있으니까요. **따로 "미리보기니까 기록하지 마" 같은 예외 처리를 안 해도 됩니다.**

`PreviewPage`는 `GET /admin/exhibitions/{date}/preview`가 관람자와 **동일한 스키마**를 주므로(API 문서 §9.12), `features/gallery`의 프레젠테이션 컴포넌트를 그대로 렌더한다. 이를 위해 갤러리 컴포넌트는 **데이터를 프롭으로 받는 순수 컴포넌트**와 **데이터를 가져오는 컨테이너**로 분리한다. 미리보기는 전자만 사용한다.

이 분리는 미리보기 하나를 위한 것이 아니라 **관람자 화면을 데이터 없이 테스트·스토리북에 올릴 수 있게** 한다.

**미리보기에서는 기록을 전송하지 않는다.** `viewTracker`는 컨테이너 계층에만 붙어 있으므로 순수 컴포넌트를 렌더하는 미리보기는 자연히 기록 경로를 타지 않는다. 별도 플래그로 억제하지 않는 것이 이 분리의 이점이다.

## 9. 성능

> **📘 쉬운 설명**
>
> **얼마나 빨라야 하는가**입니다. 숫자로 목표를 정해두면 나중에 "빠른가?"를 두고 감으로 다투지 않습니다.
>
> - **LCP 2.5초** — 화면의 가장 큰 것(여기서는 그림 격자)이 2.5초 안에 떠야 합니다
> - **CLS 0** — 로딩 중에 화면이 덜컥거리며 밀리지 않아야 합니다
> - **하루 3MB** — 매일 쓰는 서비스에서 데이터 요금 부담이 되면 안 됩니다

### 9.1 목표 (PRD §8.1)

| 지표 | 목표 | 대상 화면 |
|---|---|---|
| LCP | ≤ 2.5초 (4G) | C 갤러리 |
| 그림 표시 | ≤ 1.5초 | C-2 |
| INP | ≤ 200ms | 전 화면 |
| CLS | ≈ 0 | 전 화면 |
| 하루치 전송량 | ≤ 3MB | 12점 열람 |

### 9.2 이미지 전략

> **📘 쉬운 설명**
>
> 그림 12장을 어떻게 빠르게 보여줄지의 전략입니다.
>
> **상위 6개만 먼저 받습니다.** 3열 격자에서 화면에 처음 보이는 건 6개 정도이고, 나머지는 스크롤해야 보입니다. 12장을 한꺼번에 받으면 첫 화면이 그만큼 늦게 뜹니다.
>
> **인접 그림 미리 받기**도 좋은 장치입니다. 3번 그림을 보고 있으면 2번과 4번을 미리 받아둡니다. 손가락으로 밀었을 때 기다림 없이 바로 나타납니다.
>
> 마지막 계산이 정직합니다 — 썸네일 420KB + 감상용 2.2MB = **2.6MB**. 목표(3MB) 안에 들어옵니다. **목표를 정했으면 계산으로 확인**해야지, "괜찮겠지"로 넘어가면 안 됩니다.

| 항목 | 규칙 |
|---|---|
| 그리드 | 상위 6개 `eager` + `fetchpriority="high"`, 나머지 `lazy` (`IntersectionObserver` rootMargin 200px) |
| 플레이스홀더 | LQIP data URL(응답에 포함, 추가 요청 0) |
| 종횡비 | 서버가 준 `aspect_ratio`로 컨테이너 예약 |
| C-2 | 진입 시 `display` 로드, **인접 그림(이전·다음) `display`를 유휴 시간에 프리페치** |
| 원본 | 전체화면 뷰어에서 확대 제스처 시작 시에만 로드. 로드 전까지 display 표시 |
| 포맷 | WebP 단일(대상 브라우저 전부 지원, PRD 부록 B) |

**전송량 산정** — 썸네일 12 × 약 35KB = 420KB, display 12 × 약 180KB = 2.2MB. 합계 약 2.6MB로 목표 이내다. 원본은 명시적 요청 시에만 나가므로 산정에서 제외한다.

### 9.3 기록 전송 규칙

> **📘 쉬운 설명**
>
> 방문·열람 기록을 **언제 보낼지**입니다.
>
> **1.5초 규칙**이 핵심입니다. 손가락으로 휙휙 넘기며 스쳐 지나간 그림까지 "봤다"고 세면, "하루 평균 몇 점을 보시나요?" 같은 지표가 의미를 잃습니다.
>
> 마지막 문단도 중요합니다 — **기록 전송이 실패해도 사용자에게 아무것도 보여주지 않습니다.** 통계 수집 실패는 사용자의 문제가 아닙니다.
>
> `sendBeacon`은 **화면을 떠나는 순간에도 확실히 보내지는** 특수한 전송 방식입니다. 일반 요청은 화면이 닫히면 중간에 끊깁니다.

| 기록 | 시점 | 조건 |
|---|---|---|
| 입장(`/exhibitions/{date}/view`) | C 화면 첫 렌더 후 | 세션당 날짜별 1회. `sessionStorage` 마커로 중복 억제 |
| 열람(`/artworks/{id}/view`) | C-2 진입 후 **1.5초 체류** | 스와이프로 스쳐 지나간 그림은 세지 않는다 |

두 요청 모두 **실패해도 재시도 1회 후 조용히 포기**한다. 사용자에게 오류를 보여주지 않는다(FA-7). 화면 이탈 중 전송이 필요하면 `navigator.sendBeacon`을 우선 사용한다.

### 9.4 프리페치

> **📘 쉬운 설명**
>
> **프리페치**는 "누를 것 같은 것을 미리 받아두는 것"입니다. 썸네일에 손가락이 닿는 순간(누르기 전!) 이미 받기 시작합니다.
>
> 마지막 문단이 배려입니다. **데이터 절약 모드를 켜뒀거나 통신이 느린 사용자에게는 미리 받기를 전부 끕니다.** 안 볼 수도 있는 것을 미리 받는 건 여유가 있을 때 이야기입니다.

| 계기 | 대상 |
|---|---|
| C 화면 렌더 완료 | 첫 번째 그림의 `GET /artworks/{id}` |
| 썸네일 `pointerdown` | 해당 그림 상세 |
| C-2 진입 | 인접 그림 상세 + display 이미지 |
| `/admin` 진입 | 오늘 날짜 편집 데이터 |

프리페치는 `navigator.connection.saveData`가 켜져 있거나 `effectiveType`이 `2g`면 **모두 비활성화**한다.

### 9.5 렌더 성능

- 12개 썸네일 그리드는 가상화하지 않는다(항목이 12개다). 대신 `React.memo`로 개별 썸네일의 리렌더를 차단한다.
- 스와이프 중 `transform`은 `requestAnimationFrame` 기반으로 갱신하고 React 상태를 매 프레임 업데이트하지 않는다.
- 관리자 회원 목록은 100행을 넘으면 페이지네이션으로 처리하며 가상화하지 않는다.

## 10. PWA · 오프라인 · 푸시

> **📘 쉬운 설명**
>
> **PWA**는 웹사이트를 앱처럼 홈 화면에 두고 쓰는 기술입니다. 앱스토어에 올리지 않고도 앱처럼 동작합니다.
>
> 이 서비스에서 PWA가 필요한 이유는 세 가지입니다.
> 1. **홈 화면 아이콘** — 68세 사용자가 원하는 "매일 같은 자리"
> 2. **알림** — 아침 7시 30분 알림
> 3. **오프라인** — 지하철에서 통신이 끊겨도 마지막 전시는 보임

### 10.1 캐시 전략 (Workbox)

> **📘 쉬운 설명**
>
> **캐시**는 받아둔 것을 저장해뒀다가 다시 쓰는 것입니다. 전략 이름의 뜻은,
>
> - **CacheFirst** — 저장된 게 있으면 그걸 쓰고, 없을 때만 받는다 (그림처럼 안 바뀌는 것)
> - **NetworkFirst** — 일단 받아보고, 실패하면 저장된 걸 쓴다 (전시 정보처럼 바뀔 수 있는 것)
> - **NetworkOnly** — 항상 새로 받는다 (관리자 화면)
>
> **오프라인 동작**이 이 표의 결론입니다. 지하철에서 통신이 끊겨도 **마지막으로 본 전시가 그대로 뜨고**, 위에 "연결이 없어 마지막으로 본 전시를 보여드립니다"라는 안내만 붙습니다. 빈 화면과 "오류가 발생했습니다"를 보여주는 것과는 완전히 다른 경험입니다.

| 자원 | 전략 | 만료 |
|---|---|---|
| 앱 셸(JS/CSS/HTML) | Precache + `CacheFirst` | 배포마다 갱신 |
| 폰트 | `CacheFirst` | 1년 |
| `/media/artworks/*` | `CacheFirst` | 30일 / 최대 200개 |
| `GET /api/v1/exhibitions/current` | `NetworkFirst` (타임아웃 3초) | 7일 |
| `GET /api/v1/exhibitions/{date}` | `NetworkFirst` | 7일 |
| `GET /api/v1/public/landing` | `NetworkFirst` (타임아웃 2초) | 1일 |
| 그 외 API | `NetworkOnly` | — |

**오프라인 동작** — 네트워크가 없으면 마지막으로 본 전시를 캐시에서 렌더하고 상단에 안내 바를 띄운다(PRD §6.5). 관리자 화면은 오프라인을 지원하지 않으며 명시적 안내를 보여준다.

### 10.2 업데이트 처리

> **📘 쉬운 설명**
>
> 새 버전이 배포됐을 때 **바로 적용하지 않습니다.**
>
> 자동으로 새로고침해버리면, **그림을 보고 있던 중에 화면이 리셋됩니다.** 그래서 아래쪽에 "새 버전이 있습니다 · 새로고침" 안내만 띄우고, 누를지는 사용자가 정합니다.

새 서비스워커가 감지되면 **즉시 갱신하지 않는다.** 하단에 `새 버전이 있습니다 · 새로고침` 안내를 띄우고 사용자가 누를 때 적용한다. 그림을 보는 도중 화면이 리로드되는 일이 없어야 한다.

### 10.3 푸시 구독 흐름

> **📘 쉬운 설명**
>
> 알림 받기를 설정하는 과정입니다. **2번이 iPhone 사용자를 위한 필수 단계**입니다.
>
> iPhone에서는 사파리로 웹사이트를 보는 상태로는 **알림을 받을 수 없습니다.** 반드시 "홈 화면에 추가"를 먼저 해야 합니다. 이 사실을 모르면 사용자는 "알림 켰는데 왜 안 와요?" 상태로 남습니다.
>
> 그래서 iPhone 사용자에게는 **권한을 묻기 전에 홈 화면 추가 방법을 그림으로 안내**합니다. 순서가 반대면 안 됩니다 — 권한을 먼저 물어 거절당하면 다시 묻기가 어렵습니다.
>
> **6번**도 중요합니다. 거절한 사람에게 다시 묻지 않습니다. 계속 물으면 서비스 자체를 지웁니다.

| 단계 | 동작 |
|---|---|
| 1 | 가입 완료 직후(PRD §6.4) 또는 C-4 설정에서 시작 |
| 2 | iOS이고 standalone이 아니면 **`IosInstallGuide`를 먼저** 표시(홈 화면 추가 안내). 권한 요청을 하지 않는다 |
| 3 | `Notification.requestPermission()` |
| 4 | 허용 시 `pushManager.subscribe(VAPID public key)` |
| 5 | `POST /me/push-subscriptions` |
| 6 | 거부 시 재요청하지 않는다. C-4에 "알림이 차단되어 있습니다 · 브라우저 설정에서 허용" 안내만 |

**구독 재검증** — 앱 부팅 시 `GET /me/push-subscriptions`로 서버 등록 목록을 받아 브라우저의 현재 구독(`endpoint`)과 대조한다. 서버에 없거나 endpoint가 바뀌었으면 재등록하고, 브라우저 구독이 사라졌는데 서버에 남아 있으면 해당 구독을 해제한다. 이 대조는 **부팅당 1회**만 수행한다.

### 10.4 서비스워커 커스텀 핸들러

> **📘 쉬운 설명**
>
> **서비스워커**는 앱이 꺼져 있어도 브라우저 뒤에서 도는 작은 프로그램입니다. 알림을 받는 것도 이 친구입니다.
>
> `notificationclick`(알림을 눌렀을 때) 처리를 보세요. **이미 열려 있는 탭이 있으면 새 창을 열지 않고 그 탭을 앞으로 가져옵니다.** 안 그러면 알림을 누를 때마다 탭이 하나씩 늘어납니다.

| 이벤트 | 동작 |
|---|---|
| `push` | 페이로드의 `title`·`body`·`url`·`tag`로 알림 표시. 파싱 실패 시 기본 문구 |
| `notificationclick` | 이미 열린 탭이 있으면 포커스 후 `/`로 이동, 없으면 새로 연다 (PRD §6.12 — 모든 진입은 A를 거친다) |
| `pushsubscriptionchange` | 재구독 후 서버 갱신 |

### 10.5 매니페스트

`display: standalone`, `orientation: portrait`, `theme_color`·`background_color`는 `--gk-bg-canvas`와 동일. 아이콘 192/512/maskable. `start_url: "/"`.

## 11. 접근성

> **📘 쉬운 설명**
>
> 시력·운동 능력에 제약이 있는 사람도 쓸 수 있게 만드는 부분입니다. 이 서비스에서는 68세 사용자가 주요 대상이라 **선택이 아니라 필수 요구사항**입니다.
>
> 특히 중요한 항목:
>
> - **스와이프 대체** — 손가락으로 미는 걸 모르는 사람을 위해 **"이전 그림 / 다음 그림" 글자 링크**를 함께 둡니다
> - **확대 대체** — 손가락 두 개로 벌리는 걸 모르는 사람을 위해 **"크게 보기" 버튼**을 둡니다
> - **포커스 이동** — 화면이 바뀌면 스크린리더가 새 화면 제목을 읽어줍니다
>
> **제스처만 있는 기능은 이 서비스에 존재하지 않습니다.**

| 항목 | 구현 |
|---|---|
| 큰 글씨 모드 | `FontScaleProvider`가 `html[data-font-scale]`을 동기화. 서버 값(`user.font_scale`)이 원천, 로컬 캐시로 초기 깜빡임 방지 |
| 포커스 관리 | 라우트 전환 시 메인 랜드마크로 포커스 이동 + 화면 제목을 `aria-live="polite"`로 알림 |
| 랜드마크 | 각 페이지 `main`, 하단 네비 `nav[aria-label]` |
| 이미지 대체 텍스트 | `{제목} – {작가}` (디자인 문서 §9) |
| 그리드 시맨틱 | `ul`/`li` + 링크. `div` 나열 금지 |
| 전체화면 뷰어 | `role="dialog"` + `aria-modal` + 포커스 트랩 + `Esc` 닫기 |
| 스와이프 대체 | 좌우 화살표 키, 화면 하단 이전/다음 텍스트 링크 |
| 확대 대체 | `크게 보기` 버튼(핀치 제스처를 모르는 사용자용, PRD §5.2) |
| 축소 애니메이션 | `prefers-reduced-motion` 전역 대응 |
| 폼 | 라벨 연결, `aria-invalid`, `aria-describedby`로 오류·힌트 연결 |
| 검증 | `axe-core`를 컴포넌트 테스트와 E2E에 통합 |

## 12. 보안

> **📘 쉬운 설명**
>
> 화면 쪽의 보안 조치입니다. 몇 개만 풀어보면,
>
> - **토큰을 `localStorage`에 저장 금지** — 브라우저 저장소에 로그인 정보를 두면 악성 코드가 읽어갈 수 있습니다. 그래서 자바스크립트가 못 읽는 쿠키에만 둡니다
> - **`dangerouslySetInnerHTML` 금지** — 남이 쓴 글을 화면에 그대로 심는 기능인데, 악성 코드가 섞여 들어올 수 있습니다. 이름부터 "위험한"이라고 붙어 있습니다
> - **작품 이미지를 링크 미리보기에 넣지 않음** — 카카오톡 미리보기 카드는 로그인 없이 만들어지므로, 여기에 작품을 쓰면 **작품이 공개 경로로 새어 나갑니다.** 그래서 미술관 정문 이미지만 씁니다

| 항목 | 조치 |
|---|---|
| 토큰 | JS가 접근하지 않는다(HttpOnly 쿠키). `localStorage`에 자격 정보 저장 금지 |
| CSRF | 모든 변경 요청에 `X-Requested-With: gallery-k` (httpClient가 자동 부착) |
| XSS | `dangerouslySetInnerHTML` 전면 금지(린트). 전시 테마·설명의 줄바꿈은 CSS `white-space: pre-line`으로 처리 |
| CSP | `default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'; script-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'` — CloudFront 응답 헤더로 주입 |
| 검색 노출 | `robots.txt` 전체 차단 + `<meta name="robots" content="noindex,nofollow">` (PRD §8.4) |
| OG | 제목·설명 텍스트 + `media/public/entrance.jpg`. **작품 이미지는 OG에 절대 넣지 않는다** |
| 로그 | 콘솔 로그에 전화번호·이름을 남기지 않는다. 프로덕션 빌드에서 `logger`가 no-op |
| 소스맵 | 프로덕션 소스맵을 공개 경로에 배포하지 않는다 |
| 의존성 | `npm audit` CI + 주 1회 갱신 PR |

### 12.1 관리자 UI 은닉의 의미

> **📘 쉬운 설명**
>
> 아주 중요한 구분입니다. **관리자 링크를 숨기는 것은 보안이 아닙니다.**
>
> 화면에서 안 보인다고 못 들어가는 게 아닙니다. 주소만 알면 누구나 칠 수 있습니다. **진짜 통제는 서버가 합니다** — 관리자가 아니면 서버가 정보를 안 줍니다.
>
> 화면에서 숨기는 건 "관람자에게 필요 없는 걸 안 보여주는" 편의일 뿐입니다. 이걸 혼동해서 "화면에서 숨겼으니 안전하다"고 생각하는 것이 보안 사고의 흔한 출발점입니다.

`Curator K` 링크를 숨기고 `/admin` 접근 시 조용히 리다이렉트하는 것은 **UI 편의일 뿐 보안이 아니다**(PRD §8.4). 실제 통제는 서버가 한다. 프런트는 이를 전제로 하며, 관리자 API 응답을 회원 화면에서 다루는 코드를 두지 않는다.

## 13. 오류 경계와 복원력

> **📘 쉬운 설명**
>
> **오류 경계**는 "여기서 터진 오류는 여기까지만"이라고 막는 울타리입니다.
>
> 이게 없으면 부품 하나에서 오류가 나도 **화면 전체가 하얗게 됩니다.** 울타리를 여러 겹 치면, 통계 카드 하나가 망가져도 나머지 화면은 멀쩡합니다.
>
> **청크 로드 실패**는 배포 직후에 흔한 문제입니다. 사용자가 옛날 화면을 열어둔 채로 새 배포가 되면, 필요한 코드 조각이 이미 사라져 있습니다. 이때 자동으로 한 번 새로고침해서 조용히 해결합니다.
>
> 마지막 문단 — **첫 화면은 어떤 API가 실패해도 뜹니다.** 기획서의 요구입니다.

| 계층 | 처리 |
|---|---|
| 루트 `AppErrorBoundary` | 렌더 예외 → 전체 화면 `ErrorState` + 새로고침 유도. `request_id`가 있으면 함께 표시 |
| 라우트 경계 | 라우트별 `errorElement`. 다른 화면으로 이동은 가능한 상태 유지 |
| 위젯 경계 | 그리드·이미지·통계 카드 등 부분 실패 격리 |
| 청크 로드 실패 | 배포 직후 흔한 문제. 자동 1회 새로고침 후 실패하면 안내 |
| 오프라인 | 상단 안내 바 + 캐시 렌더 |

**A 첫 화면은 예외다.** 어떤 API가 실패해도 정문 이미지와 버튼이 보이도록, `LandingPage`는 데이터 없이도 완전한 레이아웃을 렌더한다(PRD §6.1).

### 14.1 반드시 있어야 하는 E2E

> **📘 쉬운 설명**
>
> **E2E 테스트**는 사람이 하듯 실제로 화면을 클릭하며 전체 흐름을 확인하는 자동 검사입니다.
>
> 여기 9개는 **"이게 망가지면 서비스가 서비스가 아닌"** 흐름들입니다. E-1(가입해서 그림 보기)이 안 되면 아무 의미가 없고, E-6(전시 올리기)이 안 되면 큐레이터가 일을 못 합니다.
>
> 마지막 문단은 화면과 서버가 어긋나는 걸 막는 장치입니다. 화면 테스트는 **가짜 서버 응답**으로 돌아가는데, 진짜 서버가 응답 모양을 바꿨는데 가짜만 옛날 모양이면 **테스트는 통과하는데 실제로는 고장난** 상태가 됩니다.

| # | 시나리오 |
|---|---|
| E-1 | 가입 → 자동 로그인 → C 진입 → 그림 열람 → 스와이프 → 갤러리 복귀 |
| E-2 | 로그인 → 연장 중인 전시에서 `8월 30일의 전시` 표시 확인 |
| E-3 | 아카이브에서 지난 전시 열기 → 오늘로 돌아가기 |
| E-4 | 설정에서 알림 끄기 → 재진입 시 유지 |
| E-5 | 큰 글씨 모드 전환 → 그리드 2열 확인 |
| E-6 | 관리자: 제목·테마 입력 → 12장 업로드 → 발행 상태 Y 전환 |
| E-7 | 관리자: 과거 미발행일의 이어쓰기 |
| E-8 | 오프라인 상태에서 C 화면 캐시 렌더 |
| E-9 | 비큐레이터가 `/admin` 직접 접근 시 갤러리로 이동 |

**MSW 핸들러는 API 문서의 응답 스키마를 그대로 구현**하며, 백엔드 계약 변경 시 핸들러 갱신이 함께 이뤄지지 않으면 통합 테스트가 실패하도록 스키마 검증을 포함한다.

## 16. 코딩 규약

> **📘 쉬운 설명**
>
> 코드를 쓰는 세부 규칙입니다. 비개발자는 넘어가도 되지만, 두 줄만 눈여겨볼 만합니다.
>
> **"주석은 무엇이 아니라 왜"** — 코드를 보면 "무엇을" 하는지는 알 수 있습니다. 알 수 없는 건 "왜 이렇게 했는지"입니다. 그래서 주석에는 이유를 적고, 기획서의 절 번호를 함께 적어둡니다.
>
> **"사용자 문구는 한 파일에"** — 화면 코드 안에 한국어 문장을 직접 쓰지 않습니다. 문구를 다듬을 때 코드 50군데를 뒤지지 않으려는 것이고, 서비스 전체의 말투를 한 번에 볼 수 있게 하려는 것이기도 합니다.

| 항목 | 규칙 |
|---|---|
| 파일명 | 컴포넌트 `PascalCase.tsx`, 훅 `useCamelCase.ts`, 그 외 `camelCase.ts` |
| 컴포넌트 | 함수 선언 + named export. default export는 라우트 lazy 대상만 |
| 타입 | `interface`는 확장 대상에만, 나머지는 `type`. `any` 금지, `unknown` 후 좁히기 |
| 프롭 | 5개 초과 시 객체로 묶거나 컴포넌트를 분해한다 |
| 훅 | 한 훅은 한 관심사. 반환값이 5개를 넘으면 분해 신호 |
| 조건부 렌더 | 삼항 중첩 금지. 2단계 이상이면 早期 return 또는 서브컴포넌트 |
| 주석 | "무엇"이 아니라 "왜". 도메인 규칙 참조는 PRD 절 번호를 적는다 |
| import | 절대 경로 별칭(`@/app`, `@/features`, `@/entities`, `@/shared`) |
| 매직 값 | `shared/config/constants.ts`. 12·30 같은 숫자를 화면에 직접 쓰지 않는다 |
| 사용자 문구 | `shared/config/messages.ts`. JSX에 한국어 문자열을 직접 쓰지 않는다(예외: 스토리북 데모) |
