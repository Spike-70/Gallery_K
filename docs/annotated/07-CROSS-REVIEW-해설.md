## 📘 초보자를 위한 안내

**교차 검토가 뭔가요?**

설계 문서 6개를 다 쓴 뒤에, **문서끼리 서로 어긋난 곳이 없는지 확인하는 작업**입니다.

왜 필요할까요? 각 문서는 자기 영역에 집중해서 쓰기 때문입니다.
- 화면 설계서는 "이 화면에는 이런 게 있다"를 씁니다
- API 명세서는 "이런 정보를 줄 수 있다"를 씁니다

그런데 화면 설계서가 **"여기에 마지막 방문일을 보여준다"**고 썼는데, API 명세서에 **그 정보를 주는 창구가 없으면**? 각 문서만 보면 아무 문제가 없습니다. **문제는 둘 사이에 있습니다.**

**왜 "역순"으로 봤나요?**

문서를 쓴 순서는 데이터베이스 → API → 디자인 → 백엔드 → 프런트엔드 → UX였습니다. 아래에서 위로 쌓아 올린 순서죠.

검토는 그 **반대로** 했습니다. 사용자가 보는 화면(UX)에서 시작해 아래로 내려가며 **"이걸 만들려면 아래층에 무엇이 있어야 하지?"**를 확인했습니다.

집으로 치면, 도면을 다 그린 뒤에 **"거실에 콘센트가 필요한데, 전기 도면에 그 선이 있나?"**를 확인하는 것과 같습니다.

**이 문서를 읽으면 좋은 이유**

설계 문서를 처음 쓰는 사람에게 특히 유용합니다. **"어떤 종류의 실수가 잘 생기는가"**를 27개의 실제 사례로 보여주기 때문입니다.

그리고 §3.1의 결론이 인상적입니다 — **심각한 문제 6개 중 5개가 "문서와 문서의 경계"에서 나왔습니다.** 각 문서는 다 잘 썼는데, 그 사이는 아무도 담당하지 않았던 것입니다.

**읽는 요령** — §2가 발견한 문제 목록, §3이 요약과 교훈, §4가 "앞으로 함께 고쳐야 할 것들"의 목록입니다. 모르는 단어는 [용어 사전](00-용어사전.md)에서. 원문은 `../07-CROSS-REVIEW.md`입니다.

## 1. 검토 방법

> **📘 쉬운 설명**
>
> 검토할 때 던진 질문이 딱 하나입니다 — **"이 문서만 보고 만들었을 때, 실제로 동작하는 것이 나오는가?"**
>
> 아래 표의 "검토 관점"이 문서마다 다른 것을 보세요. UX 문서를 볼 때는 "화면 사양이 빠진 게 없나", 데이터베이스 문서를 볼 때는 "API가 주기로 한 정보를 실제로 만들어낼 수 있나"를 봅니다.
>
> **같은 눈으로 전부 훑는 게 아니라, 문서마다 다른 질문을 던지는 것**이 이 검토의 방법입니다.

작성 순서(DB → API → 디자인 → 백엔드 → 프런트 → UX)의 **역순**으로 문서를 훑으며, 아키텍처 두 문서가 전제하는 계약이 하위 문서에 실재하는지 확인했다. 각 문서를 볼 때 던진 질문은 하나다.

> **"이 문서만 보고 구현했을 때, 아키텍처가 기대하는 것을 만들 수 있는가?"**

검토 순서와 관점:

| 순서 | 문서 | 검토 관점 |
|---|---|---|
| 1 | `06-USER-EXPERIENCE` | 프런트 라우팅 표에 있는 모든 화면의 UX 사양이 존재하는가. 화면 상태 전수가 정의되었는가 |
| 2 | `05-FRONTEND-ARCHITECTURE` | UX가 요구하는 문구·컴포넌트·경로를 담을 자리가 구조에 있는가. API 계약을 소비할 수 있는가 |
| 3 | `04-BACKEND-ARCHITECTURE` | 미들웨어·서비스·배치가 DB·API 문서의 요구를 빠짐없이 수행하는가. 실행 순서에 모순이 없는가 |
| 4 | `03-DESIGN-SYSTEM` | UX가 지시하는 모든 UI 요소가 카탈로그에 있는가. 상태 종류가 일치하는가 |
| 5 | `02-API-SPEC` | 프런트가 호출하는 모든 경로가 존재하는가. 응답 스키마에 이름이 있는가 |
| 6 | `01-DATABASE-MODEL` | API 응답의 모든 필드가 산출 가능한가. 산출 방법이 N+1을 유발하지 않는가 |

## 2. 식별된 문제와 조치

> **📘 쉬운 설명**
>
> 발견한 문제 27개입니다. **심각도**의 뜻은,
>
> - **높음** — 그대로 만들면 **동작하지 않거나** 사용자가 길을 잃는다
> - **중간** — 만드는 사람이 알아서 판단하게 되어, 나중에 문서와 다른 결과가 나온다
> - **낮음** — 빠진 참조나 이름
>
> 각 항목에 **"문제"와 "조치"가 짝**으로 적혀 있습니다. 발견만 하고 안 고치면 목록의 의미가 없습니다.

심각도 기준 — **높음**: 그대로 구현하면 동작하지 않거나 사용자가 길을 잃는다 / **중간**: 구현자가 임의 결정을 하게 되어 문서 간 불일치가 생긴다 / **낮음**: 누락된 참조·명명.

### 2.1 `06-USER-EXPERIENCE`

> **📘 쉬운 설명**
>
> **X-03(아카이브 문맥 유실)**이 이해하기 쉬운 예입니다.
>
> 상황: 지난 전시 목록에서 8월 30일 전시를 열고, 그 안의 그림 하나를 봅니다. 그리고 "갤러리 화면으로"를 누르면?
>
> 원래 설계대로면 **오늘의 전시로 튕겨 나갑니다.** 8월 30일 전시로 돌아가려던 사람은 갑자기 다른 곳에 와 있게 되죠.
>
> 왜 이런 일이 생겼을까요? "지난 전시 화면"과 "그림 화면"이 각각 잘 설계되어 있었는데, **그 둘을 이어붙였을 때 어디로 돌아가야 하는지**는 어느 문서도 정하지 않았기 때문입니다.
>
> **X-02(비밀번호 변경 화면의 탈출구)**도 흥미롭습니다. "모든 화면에 되돌아가기가 있어야 한다"는 원칙과 "초기 비밀번호는 반드시 바꿔야 한다"는 요구가 **정면으로 부딪칩니다.** 이럴 때 그냥 넘어가지 않고 "원칙의 예외로 명시하고, 대신 로그아웃을 둔다"고 결론을 내린 것이 좋은 처리입니다.

| ID | 심각도 | 문제 | 조치 |
|---|---|---|---|
| X-01 | 높음 | 프런트 라우팅 표에 있는 **A-2 비밀번호 재설정 · 비밀번호 변경 · 미리보기 · 404/오류** 화면의 UX 사양이 없었다. 라우트는 있는데 무엇을 그릴지 결정되지 않은 상태 | §3.4·§3.5·§3.18·§3.19 신설 |
| X-02 | 높음 | `must_change_password` 계정이 강제로 들어가는 비밀번호 변경 화면에 **되돌아가기가 있으면 초기 비밀번호로 서비스를 계속 쓸 수 있다.** 반대로 없으면 UX-3 위반이자 사용자가 갇힌다 | UX-3의 명시적 예외로 규정하고 `로그아웃`을 탈출구로 배치 |
| X-03 | 높음 | **아카이브에서 연 그림의 되돌아가기 대상이 없었다.** 지난 전시를 보다 그림을 열고 돌아가면 오늘의 전시로 튕겨 나간다 | `이 전시로` 되돌아가기 규약 추가(§2.3), 여정 §4.3 갱신. 프런트에 전용 경로 추가(X-08) |
| X-04 | 중간 | 관리자 화면의 오프라인 동작이 정의되지 않았다(프런트는 미지원으로 명시) | B 화면 상태 표에 오프라인 행 추가 |
| X-05 | 낮음 | 개관 전 과거 날짜의 관리자 상태 칩이 정의와 충돌(`N`은 오늘·미래만) | 예외 상황임을 §3.11에 명기 |
| X-06 | 낮음 | 새로 정의한 화면의 버튼 문구가 마이크로카피 카탈로그에 없었다 | §5.2에 9개 항목 추가 |

### 2.2 `05-FRONTEND-ARCHITECTURE`

> **📘 쉬운 설명**
>
> **X-09(미디어 쿠키 갱신)**가 심각한 이유를 풀어보면,
>
> 그림 이미지는 아무나 못 보게 되어 있고, 로그인한 사람만 **6시간짜리 임시 열쇠**를 받습니다. 그런데 이 열쇠를 **누가 언제 갱신하는지**가 어느 문서에도 없었습니다.
>
> 그대로 만들면 어떻게 될까요? 앱을 켜고 6시간 뒤에 **모든 그림이 한꺼번에 안 보이게** 됩니다. 그림이 전부인 서비스에서 이건 치명적입니다.

> 게다가 이런 문제는 **개발 중에는 절대 안 잡힙니다.** 개발자가 6시간 동안 화면을 켜둔 채로 테스트하지 않기 때문입니다.

### 2.3 `04-BACKEND-ARCHITECTURE`

> **📘 쉬운 설명**
>
> **X-14(미들웨어 순서 모순)**가 이 검토에서 가장 명백한 오류였습니다.
>
> 원래 설계는 이 순서였습니다.
> 1. 로그인 확인
> 2. 데이터베이스 연결
>
> 그런데 **로그인을 확인하려면 데이터베이스를 읽어야 합니다.** (그 사람의 비밀번호가 바뀌지 않았는지 대조해야 하니까요.) 즉 **1번을 하려면 2번이 먼저 되어 있어야 하는데, 순서가 반대**였습니다.
>
> 그대로 만들면 **모든 요청이 실패합니다.**
>
> 왜 이런 게 안 보였을까요? 두 항목이 각각은 완벽하게 설명되어 있었기 때문입니다. **"둘의 순서"는 어느 절의 주제도 아니었습니다.**
>
> 고친 방법도 참고할 만합니다. 단순히 순서만 바꾸면 로그인 안 한 요청까지 데이터베이스 연결을 잡아먹으므로, **"연결 준비만 해두고 실제로는 쓸 때 연결한다"**는 방식으로 두 문제를 함께 해결했습니다.

| ID | 심각도 | 문제 | 조치 |
|---|---|---|---|
| X-14 | **높음** | **미들웨어 순서 모순** — `authentication`이 `db_session`보다 바깥에 있었다. 그러나 인증은 `token_version` 대조를 위해 DB를 읽어야 한다. 초안대로면 인증 단계에서 세션이 없다 | `db_session`을 `authentication` 바깥으로 이동하되 **지연 생성**으로 변경. 미인증·`304` 요청이 커넥션을 점유하지 않는다 |
| X-15 | 중간 | DB 문서의 운영 배치 6종 중 `push_subscription_prune`이 백엔드 잡 목록·디렉터리에서 누락 | `jobs/push_subscription_prune.py` 및 배치 표에 추가 |
| X-16 | 중간 | `notification_log.kind`의 `late_publish`가 열거형에만 있고 **어느 경로에서 쓰이는지 미정의** | 발송 워커 §9.2에 정의 — 예약 발송은 `morning_exhibition`, 알림 시각 경과 후 발행분은 `late_publish`. 늦은 발행의 도달률을 사후 분리 관측하기 위함 |
| X-17 | 낮음 | 서명 방식 전환(`cookie`/`url`)이 호출부로 새어 나갈 구조 | `media_service` 내부로 캡슐화함을 명시 |

### 2.4 `03-DESIGN-SYSTEM`

> **📘 쉬운 설명**
>
> **X-18**은 단순한 누락입니다. UX 문서가 "여기에 필터 칩을 둔다", "여기에 ⋯ 메뉴를 둔다"고 썼는데, **디자인 규격집에 그 부품이 없었습니다.**
>
> 그대로 두면 개발자가 그때그때 만들어내고, 화면마다 조금씩 다른 필터 칩이 생깁니다.
>
> **X-19**는 조금 미묘한 문제입니다. 서버는 이미지 상태를 5가지로 관리하는데, 화면에서는 6가지로 보여야 합니다. 왜냐하면 **"이미지는 준비됐지만 설명을 아직 안 쓴 상태"**와 **"이미지도 설명도 다 된 상태"**를 큐레이터가 구별해야 하기 때문입니다.
>
> **서버가 아는 것과 화면이 보여줘야 하는 것이 1:1이 아닐 수 있다** — 이걸 놓치면 화면이 부족해집니다.

| ID | 심각도 | 문제 | 조치 |
|---|---|---|---|
| X-18 | 중간 | UX가 지시하는 **상단 안내 바 · 필터 칩 · ⋯ 메뉴 · 업로드 진행률 링 · 시각 선택 시트 · 날짜 입력**이 카탈로그에 없었다 | `Banner`·`FilterChip`·`Menu`·`ProgressRing`·`TimeSelectSheet`·`DateField` 6종 추가 |
| X-19 | 중간 | `SlotButton`을 "상태 5종"으로 정의했으나 UX는 6가지 모습을 요구 — 서버 `image_status`(5종)에 **메타데이터 완성 여부**가 곱해진다 | 시각 상태 6종으로 정정하고 파생 관계를 명기 |

### 2.6 `01-DATABASE-MODEL`

> **📘 쉬운 설명**
>
> **X-25**는 성능 문제입니다.
>
> 관리자의 회원 목록에는 회원마다 **"마지막 방문일"**과 **"알림 받고 있는지"**가 표시되어야 합니다. API 명세서에 그 항목이 있었죠.
>
> 그런데 이 두 정보는 **다른 표에 들어 있습니다.** 아무 생각 없이 만들면 회원 한 명당 두 번씩 추가로 데이터베이스에 물어보게 되고, 회원이 100명이면 **201번**을 묻습니다.
>
> 이게 바로 **N+1 문제**라고 부르는, 화면이 느려지는 가장 흔한 원인입니다. 개발자가 10명으로 테스트할 때는 멀쩡하다가, 실제 사용자가 늘면 갑자기 느려집니다.
>
> 그래서 **"이 정보는 이렇게 한 번에 가져온다"**를 미리 적어뒀습니다.

| ID | 심각도 | 문제 | 조치 |
|---|---|---|---|
| X-25 | 중간 | **`MemberItem`의 `last_viewed_on`·`push_status`·`push_platforms`가 응답 스키마에만 있고 산출 방법이 없었다.** 그대로 구현하면 회원 행마다 2회씩 질의하는 N+1 | §7.2 Q12 신설 — `LATERAL` 결합 단일 질의, 파생 필드 정렬 시의 순서 역전, 규모 초과 시의 비정규화 시점까지 규정 |

## 3. 검토 결과 요약

> **📘 쉬운 설명**
>
> 27건을 문서별·심각도별로 센 표입니다.
>
> 숫자 자체보다 **분포**를 보는 게 유용합니다. UX와 프런트엔드에 문제가 많은데(13건), 이 둘이 **가장 나중에 쓰인 문서이자 다른 모든 문서에 의존하는 문서**이기 때문입니다.
>
> 마지막 문장 — **27건 전부 반영 완료**. 그리고 각 문서에 "교차 검토"라고 표시를 남겼습니다. 나중에 "이 항목은 왜 있지?"라고 물었을 때 답이 남아 있습니다.

| 문서 | 높음 | 중간 | 낮음 | 계 |
|---|---:|---:|---:|---:|
| `06-USER-EXPERIENCE` | 3 | 1 | 2 | 6 |
| `05-FRONTEND-ARCHITECTURE` | 2 | 3 | 2 | 7 |
| `04-BACKEND-ARCHITECTURE` | 1 | 2 | 1 | 4 |
| `03-DESIGN-SYSTEM` | 0 | 2 | 2 | 4 |
| `02-API-SPEC` | 0 | 2 | 1 | 3 |
| `01-DATABASE-MODEL` | 0 | 1 | 2 | 3 |
| **합계** | **6** | **11** | **10** | **27** |

**27건 모두 해당 문서에 반영 완료**했으며, 각 문서 말미의 "PRD 대비 변경·보완 사항" 표에 `교차 검토` 표시로 이력을 남겼다.

### 3.1 문제가 몰린 지점

> **📘 쉬운 설명 — 이 문서에서 가장 중요한 부분**
>
> 심각한 문제 6개 중 **5개가 "화면과 화면 사이", "문서와 문서 사이"**에서 나왔습니다.
>
> 굵은 문장이 결론입니다 — **"각 문서는 자기 영역 안에서 충실했지만, 경계는 어느 문서의 소유도 아니었다."**
>
> 이건 설계뿐 아니라 조직에서도 똑같이 벌어지는 일입니다. 각 팀이 자기 일을 잘해도, **아무도 담당하지 않는 틈**에서 문제가 터집니다.
>
> 그래서 이런 교차 검토가 필요합니다. **누구의 일도 아닌 곳을 일부러 보는 작업**입니다.

높음 6건 중 **5건이 "화면과 화면 사이"**에서 나왔다.

- 라우팅 표에는 있으나 UX 사양이 없던 화면 (X-01)
- 강제 이동된 화면에서 나가는 길 (X-02)
- 아카이브 문맥이 그림 화면으로 이어지지 않는 문제 (X-03, X-08)
- 미디어 쿠키를 누가 갱신하는가 (X-09)

각 문서는 자기 영역 안에서 충실했지만, **경계는 어느 문서의 소유도 아니었다.** 나머지 1건(X-14 미들웨어 순서)도 같은 성격이다 — 인증과 DB 세션은 각각 정의되어 있었으나 둘의 순서는 어느 절의 주제도 아니었다.

### 3.2 이후 검토에서 다시 볼 지점

> **📘 쉬운 설명**
>
> **"이런 종류의 실수가 또 생길 것 같으니, 다음에 이런 걸 만들 때는 여기부터 확인하라"**는 목록입니다.
>
> 발견한 문제를 고치는 것으로 끝내지 않고, **같은 유형의 문제가 재발하지 않을 방법**까지 적어둔 것입니다.
>
> 예를 들어 "API에 항목을 추가할 때는 데이터베이스 문서에 그 항목을 만드는 방법도 함께 추가한다" — 이 규칙 하나가 X-25 같은 문제를 앞으로 막아줍니다.

| 항목 | 이유 |
|---|---|
| 화면 전이 시 되돌아가기 대상 | X-03과 같은 유형이 다른 경로에서 재발할 수 있다. 새 화면을 추가할 때 §2.3 표를 먼저 갱신한다 |
| 응답 스키마의 파생 필드 | X-25 유형. API에 필드를 추가할 때 DB 문서 §7에 산출 질의를 함께 추가한다 |
| 열거형 값의 사용처 | X-16 유형. 값을 추가할 때 어느 코드 경로가 그 값을 쓰는지 함께 적는다 |
| 미들웨어·초기화 순서 | X-14 유형. 새 미들웨어를 넣을 때 의존 자원(세션·설정·시크릿)의 준비 시점을 확인한다 |

## 4. 문서 간 계약 요약

> **📘 쉬운 설명**
>
> **여러 문서가 함께 지켜야 하는 값들**의 목록입니다. 한쪽만 바꾸면 반드시 어긋나는 것들이죠.
>
> **"소유 문서"** 열이 핵심입니다. 같은 정보가 여러 문서에 나올 때, **어느 문서가 원본인지**를 정해둔 것입니다. 나머지는 그것을 베낀 사본이고, 고칠 때는 원본부터 고칩니다.
>
> 예를 들어 "그림은 12점"이라는 숫자는 여러 문서에 나오지만, 원본은 데이터베이스 설정 표입니다. 만약 나중에 "12점이 너무 많으니 7점으로 줄이자"가 되면, **여기서부터 시작해서 이 표에 적힌 곳들을 따라가며** 고치면 됩니다.
>
> 이 표가 있으면 **"어디를 다 고쳐야 하지?"**를 기억에 의존하지 않아도 됩니다.
